## 1~3 기록 (2026-11-12)

이미 있던 것: 10Hz 전송 제한, 걸을 때만 전송, 100ms 보간, 끊기면 1~15초 간격 재연결, 정원 초과 화면, 공간이 차면 허브로 돌아가기.

바꾼 것:
- **혼자면 위치를 보내지 않는다.** 누가 들어오면 join 때 지금 상태를 바로 보낸다.
- **인원과 지금 걷는 사람 수에 따라 전송 간격을 늘린다**(`stateIntervalFor`): 2~10Hz. 걷는 사람 × 전송률 × 인원이 방 하나 초당 60건 안쪽이 되게 한다.
- **하트비트 2초 → 15초**, 같이 있는 사람이 있을 때만. 같은 상태는 다시 보내지 않는다.
- **받는 쪽 보간**: 다른 사람이 움직일 때마다 내 기록이 중복되어 걸음이 끊겨 보이던 문제를 고쳤다. 보간 지연은 도착 간격에 맞춰 100~700ms로 조절한다.
- **재연결 보강**: 네트워크가 돌아오거나 화면으로 돌아오면 바로 다시 붙는다. 다시 붙는 사이 정원이 찼으면 혼자 둘러보며 30초마다 다시 본다(전에는 그대로 멈췄다). 뒤로가기 캐시로 돌아온 페이지도 다시 연결한다.
- Local·ws 모드는 메시지 과금이 없어 그대로 둔다.

추정(정지 상태 2명, 하루 8시간, 30일): 전 하트비트 2초 → 월 약 173만 건, 후 15초 → 월 약 23만 건.

### 남은 문제
- 동시에 많이 걷는 10명 이상은 아직 무료 한도(초당 100)를 넘는다. 2Hz보다 더 줄이지는 않았다(1초 간격이면 기록 사이를 직선으로 이어 아바타가 모서리를 가로질러 가구를 뚫고 지나가 보일 수 있어서, 시험하지 않음). 넘으면 Supabase가 연결을 끊고, 이 코드가 다시 붙는다(완전히 멈추지는 않음). 근본 대책은 제안 11(목적지 동기화) 또는 9(방 서버).
- presence 명단 이벤트(입장·퇴장, 무료 초당 20)는 따로 재지 않았다.
- 재연결 보강(온라인 복귀·화면 복귀·bfcache·정원 찬 채 재연결)은 코드로만 확인했고 부하 테스트에 넣지 않았다.
- 기존 e2e(`tests/e2e.spec.ts`) 4개는 이번 변경 전 코드(HEAD 2807b84)에서도 같은 2개(Local 모드, 접근성)가 실패한다. 이번 변경과 무관한 기존 문제로, 따로 고쳐야 한다(PROGRESS의 confirmBook 메모 참고).

## 11 기록 (2026-11-14)

문제: 걷는 동안 위치를 초당 2~10번 보내서, 여러 명이 함께 걸으면 Supabase 무료 한도(초당 100건)를 넘었다.

바꾼 것:
- 클릭해서 걸을 때 **남은 경로를 한 번만** 보낸다(`PlayerState.path`·`pathId`). 받는 쪽은 같은 속도로 그 길을 따라 걷고(`Actor.followRoute`), 도착 소식이 오면 남은 길을 서둘러 마친다. 중간에 멈추거나 방향을 바꾸면 새 상태로 바로 옮겨 간다.
- 앉기·일어나기는 시작·자세 바뀜·끝 세 번만 보낸다. 키보드(WASD) 걷기만 예전처럼 위치를 계속 보낸다.
- 하트비트 15초 → 30초.
- 옛 버전 브라우저와 섞여도 동작한다(옛 버전은 `path`를 무시하고 위치 기록으로 움직인다. 새 버전이 보낸 걸음은 옛 버전 화면에서 직선으로 미끄러져 보일 수 있다 — 캐시가 갱신되면 사라진다).

탭 2개 확인: 앉기(자리·자세 일치), 걷다가 방향 바꾸기 모두 멈춘 뒤 오차 0.

남은 것:
- **월 200만 건 한도**가 이제 더 좁은 문이다. 봇처럼 10명이 쉬지 않고 걸으면 15시간쯤이면 다 쓴다. 실제 방문객은 훨씬 덜 걷지만, Supabase 대시보드(Reports → Realtime)에서 월 사용량을 가끔 확인해야 한다. 넘으면 제안 9(방 서버).
- 정원 20명 동시 테스트는 이 컴퓨터 GPU로 20개 화면을 못 띄워 하지 않았다(10명까지 실측).
